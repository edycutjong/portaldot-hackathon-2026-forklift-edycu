# Developer-experience report (v0)

Friction hit while building Forklift on 2026-10-14 (first day of the build window), on one machine: macOS 26 on
Apple silicon (arm64), Python 3.11.1, the `portaldot_dev` 2.0.0 release from
`portaldotVolunteer/Portaldot-node`, and the public mainnet node `wss://mainnet.portaldot.io` (runtime spec 1002). Only
things measured in this repository are listed. Each row says how to see it again. This is v0: one host, one day, no
Linux run.

| # | Friction | What we measured | How to see it | What Forklift does about it |
|---|---|---|---|---|
| 1 | **The official macOS binary is x86_64 only.** | `portaldot_dev --version` prints `2.0.0-unknown-x86_64-macos`; `file` says Mach-O x86_64; the host is arm64. It runs under Rosetta. | `~/.cache/forklift/bin/portaldot_dev --version`; `evidence/fork-2725953.json` → `binary`; `evidence/bench-lift-2026-10-14.json` → host | `forklift up` records the binary's version and sha256 in the fork manifest and turns "Bad CPU type" / "Exec format error" into a hint to install Rosetta (`forklift/node.py`, tested in `tests/test_node.py`). |
| 2 | **`--ws-port` is the WebSocket port and `--rpc-port` is the HTTP port** on this build, so a launcher that assumes one port serves both gets the wrong one. | The node's own `--help` text: `--rpc-port` "Specify HTTP RPC server TCP port", `--ws-port` "Specify WebSockets RPC server TCP port". A fork started with `--ws-port 59944 --rpc-port 59933` answered WebSocket on 59944 and HTTP on 59933 (`evidence/fork-2725953.json`, all fork rows in `docs/PROOF.md`). | `portaldot_dev --help \| grep -A1 -E 'ws-port\|rpc-port'` | `node_args()` passes both explicitly; `tests/test_node.py` pins the pair; the fork endpoint in every manifest is the WebSocket one. |
| 3 | **`--port` cannot be combined with `--listen-addr`** on this build. | Starting the node with both flags exits at once with `error: The argument '--listen-addr <LISTEN_ADDR>...' cannot be used with '--port <PORT>'` (reproduced on 2026-10-14 on spare ports; no node started). Forklift passes only `--listen-addr /ip4/127.0.0.1/tcp/<p2p>`, which also keeps the p2p socket on loopback. | `portaldot_dev --dev --tmp --port 59949 --listen-addr /ip4/127.0.0.1/tcp/59949`; `node_args()` and the "rejects a flag combination" hint in `forklift/node.py` | Single flag, loopback only, plus `--reserved-only --no-mdns --no-prometheus --no-telemetry` and an empty boot-node list so a fork never peers (`system_health` peers = 0 is checked after boot). |
| 4 | **The SCALE type preset matters.** | Spec 1002's `AccountInfo<Index, AccountData>` decodes to the byte (80 bytes) only with the SDK's `legacy` preset; the `polkadot` preset has no decoder for it. The pinned whale decodes to free 2×10^22 planck. | `tests/test_tx.py::test_decode_whale_account_with_legacy_preset` | `tx.py` fixes the preset to `legacy` and builds the extrinsic envelope itself, with exactly the seven signed extensions of spec 1002 (any other list is refused). |
| 5 | **Contracts is the rent era.** A contract whose balance does not cover its deposit pays rent every block and is evicted. | For the 169-byte Receipt the pallet charged rent as if 481 bytes were stored; at deploy the measured charge was up to 4,806,188,447 planck per block, about 12.1 days to eviction (`rent_top_up` row in `docs/PROOF.md`). After a top-up to the deposit bound plus 10 % no rent was charged across the next call. | `docs/PROOF.md` → *Fork Receipt contract*; `evidence/txs-2725953.json` | `forklift receipt` measures the rent, tops the contract up, and exits `6` if rent is still charged after the top-up. |
| 6 | **A successful `Sudo` extrinsic does not mean the call it carried succeeded.** | A `Sudo.sudo_as(Balances.transfer)` of more than the whale holds lands as a successful extrinsic whose `SudoAsDone` carries `Balances.InsufficientBalance`. | `tests/test_act_live.py` (`pytest -m live`), `docs/EXIT-CODES.md` (exit `5`) | `fund` and `as` decode `Sudid` / `SudoAsDone` and exit `5` when the carried call failed; evidence rows record both results. |
| 7 | **The node never returns the key equal to a paging start key**, so a draw that starts exactly on an item prefix would skip the item's bare-prefix key. | Found while building `verify`: paging starts strictly after the start key. | `forklift/verify.py` (comment at the bare-prefix read), `tests/test_verify.py` | The bare-prefix key is read with `state_getStorage`. |
| 8 | **Spec 1002 has storage its own metadata does not describe.** | AuthorityDiscovery `Keys` / `NextKeys`, the Session `Historical` items, and a pallet-version key per pallet are present in state but not in the V13 metadata storage section; without naming them every lift would report unknown keys. | `forklift/metadata.py` (`UNLISTED_ITEMS`); `evidence/lift-2725953.json` → `per_pallet` (every key has a pallet name; `AuthorityDiscovery` 3, `Historical` 1) | Named by matching `twox128` of the pallet and item names. |
| 9 | **Reading a fork's genesis state later needs an archive node.** | `verify` compares the fork at block 0 with mainnet at the pin, after the fork has finalized many more blocks; a pruned database would no longer have block 0. | `forklift/node.py` passes `--pruning archive` | Every fork runs `--pruning archive`. |

## Not measured here

- Whether the official **Linux** binary behaves the same: it was not run in this window.
- Whether the node's **log is block-buffered** off a TTY: a log file written by Forklift's own launch was within about
  2 seconds of the chain head at the one sample taken, so it did not reproduce here. Forklift reads readiness over RPC
  (`chain_getHeader`, `chain_getFinalizedHead`) and never from the log either way.
- Anything about the **V3 testnet**: no public V3 node binary or chain spec exists and its RPC did not resolve in DNS
  on 2026-10-14.
