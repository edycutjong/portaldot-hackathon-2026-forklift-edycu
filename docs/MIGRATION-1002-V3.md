How to read the headings:

- **carries over**: V3 has the same prefix and item with the same key hashers, key types and value type (shape and field names); the lifted bytes are valid on V3 as they are.
- **needs re-encoding**: V3 has the item but a key or value type differs (or the item moved). `layout-compatible` means the bytes would still parse under V3's type; the meaning of renamed fields has to be mapped by hand.
- **no home on V3**: V3 has no such item (or it is the chain's own, like `:code`).

**Reader self-check.** The type reader is also run on mainnet's own values under the resolved 1002 types: 88 of 93 sampled items parse in full; the 5 that do not (`Authorship.Uncles`, `Identity.IdentityOf`, `Session.NextKeys`, `Session.QueuedKeys`, `System.BlockWeight`) carry a caution in their row, because the SDK's 1002 type for them is incomplete.

## Limits

- Classification is by metadata shape and a value sample, not by what a V3 pallet *means* by a field: a renamed field with the same layout is reported as needing re-encoding on purpose.
- Only the top trie is lifted; the MMR range is skipped by the lift and is not counted.
- `carries over` means the encoding is valid on V3; V3's own runtime would still have to accept the state (consensus keys, pallet storage versions and the like are not meant to be copied).
